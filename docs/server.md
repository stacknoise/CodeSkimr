# Local server (WP-41)

`codeskimr serve` starts the local server: REST generated from the command registry, a WebSocket with the domain events, and the protection that blueprint S-04 asks for. The decisions are in ADR 0024. WP-42 added the browser UI delivery, the launch code and the CSP (ADR 0028, ADR 0030). The OpenAPI document is not part of these packages.

## Structure

- `codeskimr_server` is a driving adapter. `CommandApi` holds the commands that are exposed over REST, `Server` builds the router, `BoundServer` serves it. It depends on `application`, `domain` and `codes` only.
- The composition root (`crates/app`, `serve.rs`) wires it: it creates the `Registry` and `CommandApi`, resolves the `Principal` once (`principal.rs`), loads or creates the installation token (`installation_token.rs`) and binds `127.0.0.1:{server.port}`.
- `commands.rs` turns a typed `Command` into a route (`expose::<C>()`, needs `DeserializeOwned` input and `Serialize` output). The call goes through `Registry::execute`, so the permission is checked there as for every other surface. Commands run on the blocking pool, never on the async runtime.

## Routes

| Route | Meaning |
|---|---|
| `GET /api/v1/commands` | the commands the caller may run: `id`, `title_key`, `description_key`, `shortcut`, `read_only` |
| `POST /api/v1/commands/{id}` | runs a command; body = JSON input (none = `null`), answer = JSON output |
| `GET /api/v1/events` | WebSocket, one JSON text message per event |
| `GET /api/v1/ui-config` | public, no secret: editor template, allowed schemes, default theme |
| `POST /api/v1/session/launch-code` | Bearer token; returns a new one-time launch code |
| `GET /api/v1/session/launch-code` | Bearer token; `pending` is true while a code waits to be used |
| `POST /api/v1/session/exchange` | body `{ "code": … }`; returns the token once (`API-403` if wrong, used or expired) |
| `/mcp` | MCP over streamable HTTP (WP-48); every request needs the Bearer token, see below |
| everything else | files of the UI folder; paths without extension give `index.html` |

Every error answer is `{ "code": "API-401", "description": "…" }` with the HTTP status of the code's class. Unknown paths give `API-201`, a wrong method `API-101` (405).

## Checks, in this order

1. `Host` is the bound address or `localhost` with the same port; `Origin`, if present, is `http://` plus one of these. Otherwise `API-402` (403). This is the protection against DNS rebinding and cross-site requests.
2. The command exists (`API-201`).
3. A command with `read_only = false`, and a command with the permission `read_source` (it returns source text, ADR 0035), needs `Authorization: Bearer <installation token>` (`API-401`).
4. The principal holds the permission of the command (`AUTH-401`, 403). This comes before the body is read: a denied caller always gets the same answer.
5. The body is at most 1 MiB (`API-501`, 413) and, if there is one, `application/json` (`API-101`).

CORS is closed: no `Access-Control-*` header is ever sent and there is no `OPTIONS` route. Every answer has `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin` and a strict `Content-Security-Policy` (no inline script or style, no framing, connections only to the own host).

## MCP at `/mcp` (WP-48)

The running app offers the MCP server of `docs/mcp.md` on the same listener, as blueprint 10.4 asks: `codeskimr serve` builds the tools once (`crates/app/src/mcp.rs`, `http_service`) and hands the `tower` service of `codeskimr_mcp::http_service` to `Server::with_mcp`. The server crate does not know `rmcp`; it only mounts a service at `/mcp`.

- **Checks:** the `Host` and `Origin` checks of step 1 come first, as for every route. Then the token: every request to `/mcp`, whatever its method, needs `Authorization: Bearer <installation token>` (`API-401`, 401), also a pure read. Tool answers carry the structure of the code, and without the token any program on this machine could read it through the open loopback port; the token proves that the caller can read the keystore, like in ADR 0035. A client such as Claude Code or Cursor is configured with the URL `http://127.0.0.1:7421/mcp` and the header `Authorization: Bearer <token>`. How the token reaches such a client is the task of the installation (the token is never shown by a command, see below).
- **Who calls:** every request runs as the principal of the composition root, the local owner in single-user mode. After 1.0 the team edition resolves a principal per personal access token and builds one handler per caller (ADR 0019); the tools check their permission as before (`rescan` needs `scan`).
- **Stateless:** every request is answered on its own with a JSON body, no session survives a request, and there is no `GET` stream. A restart of the app loses nothing; a client that sends `Mcp-Session-Id` is not tracked. The body is at most 1 MiB.
- **Shared instance:** the service uses the database file of the app and the event bus of the server. A `rescan` of an agent publishes the same events as a scan from the UI, so the UI shows its progress. The store is opened a second time next to that of the commands (one connection each, same file); sharing the connection waits until the commands take a store from the composition root.
- **Projects:** the app has no default project. A call that names none is `MCP-101` with `params.detail = project`; the ids come from `projects.list` over REST. An MCP tool that lists the projects is not part of WP-48.
- **Not yet:** the resources (`codeskimr://…`) belong to the MCP server itself, not to this transport.

## The installation token

`csk_` and 64 hex digits (256 random bits), created at the first `serve` and kept in the credential store (OS keystore). The server keeps the BLAKE3 digest for checking requests. The token text is read in `installation_token::digest_of` and, while a launch code is waiting, held as a secret string (see below); it is never logged and not part of any `Debug` output. The prefix is masked by the log redaction (S-01). There is no command that shows the token. The browser UI gets it through a launch code:

1. `codeskimr open` reads the token from the keystore and asks the server for a code (128 random bits, valid `ui.launch_code_seconds`, default 60, usable once, one code at a time).
2. It writes a redirect page to a launch file (mode 0600, created exclusively, in a private folder with mode 0700; on Windows the folder gets access rules for the user alone) and starts the browser with that `file://` path. The folder and everything above it must belong to the user or the administrator and must not be writable by everybody (unless sticky); otherwise the file is not created (`APP-202`). The code is never on a command line. `--no-browser` only prints the path.
3. The page redirects to `http://127.0.0.1:PORT/#code=…`. The fragment is not sent to the server. The UI removes it with `history.replaceState`, then posts the code to the exchange route and keeps the token in `sessionStorage` only.
4. `open` polls until the code is taken or has expired and then deletes the file.

Threat note: `codeskimr open` sends the token to the port of `server.port` over plain HTTP on the loopback address. If no server runs there, another local user could listen on that port and read it. This is an accepted risk of the single-user mode (ADR 0030). The server holds the token text for at most the life of the code. Another OS user cannot read the launch file (0600 in a 0700 folder). A process of the same user could read it, but that user can read the keystore anyway. Within the 60 seconds a local process that guesses the code would need 2^128 tries, and a wrong code does not burn the valid one. A used or expired code is gone for good.

## Events

Messages have a `type` and ids and counts only: `scan_progressed` (`project`, `stage`, `done`, `total`, `elapsed_ms` = milliseconds since the stage started; a stage reports once more when it is over, with its last counts and its whole time), `snapshot_created` (`project`, `snapshot`), `files_changed` (`project`, `files`, `rescan`), `scan_stopped` (`project`, `reason` = `cancelled` or `failed`, `code`). The stream needs the `read` permission; messages from the client are ignored (limit 1 KiB). A thread per connection carries the events from the bus (which is synchronous) to a bounded queue (256 events) of the runtime and ends when the socket is gone. A client that does not keep up and fills the queue, or does not take a message within 10 seconds, is disconnected (close code 1013, "try again later") and connects again. An idle stream is pinged every 20 seconds and ends if it hears nothing for 90 seconds. At most 16 streams run at once; one more gets `API-502` (503).

## Limits against clients that hold resources

The server holds at most 256 connections; a further client waits in the backlog of the system until a slot is free. The server speaks HTTP/1 only. A connection that does not finish the head of its request within 10 seconds, also one that sends nothing at all, is closed (hyper's `header_read_timeout`), and the body of a JSON request to a command or to the session routes has 30 seconds, then `API-503` (408); the MCP route is not covered yet (#273). Running commands have no time limit of their own: a scan may take as long as it needs. On shutdown the event streams get a close frame (1001) and open connections have 5 seconds to finish. This stops a client that opens connections and sends nothing, or sends a byte at a time, but is no replacement for a reverse proxy in the server mode of the team server (ADR 0019).

## Configuration

`server.port` (default 7421, must not be 0). `editor.url_template` and `editor.allowed_schemes` (the link of "open in editor"), `ui.default_theme`, `ui.dir` (the folder of the built UI, default `ui`) and `ui.launch_code_seconds` (default 60). A taken port fails with `API-301`. The address is not configurable. `editor.*` and `ui.*` are read from the default, the user file and flags only: the `.codeskimr.toml` of a scanned project cannot set them (ADR 0041). `editor.allowed_schemes` cannot name `javascript`, `data`, `file` or `vbscript` (`CFG-101`). Files below `ui.dir` that are links are not served, and a `ui.dir` outside the data folder is logged as a warning. Every answer carries a `Permissions-Policy` that switches off camera, microphone, location, payment and USB.

## Known limits

- The commands of the UI are registered in `crates/app/src/ui_commands/` (`command_api`): `projects.list` (read), `projects.add` (register_project, scan), `projects.rescan` (scan), `projects.cancel` (scan), `credentials.list` (read), `credentials.set` and `credentials.delete` (both register_project), `explorer.outline` and `explorer.symbol` (both read), `search.query` (read), `status.info` (read), `usages.query` (read), `explorer.source` (read_source), `usages.code` (read_source), `graph.layers` (read). Feature packages add theirs there. `explorer.outline` takes a project id and returns the layers, namespaces and types of its newest snapshot (the layers of the project; types that belong to none come last with an empty layer name); `explorer.symbol` takes a project id and a symbol id and returns the symbol with `layer` (the name of the layer of the project that owns it, `null` if none does), breadcrumb, metrics (with a rating against the configured thresholds) and member table. An unknown symbol is `MCP-202`. A project without a scan gives `explorer.outline` an empty outline with `snapshot: null`, and `explorer.symbol` the error `MCP-203`. `projects.add` takes an absolute folder path or a Git address without credentials, and for a Git source optionally `credential`, the name of a stored login (`credentials.set`; a folder, an empty name or the installation token gives `PRJ-101`); `projects.rescan` a project id; both run the scan on the thread of the call, publish progress on the event bus of the WebSocket and refuse a second scan of the same project with `PRJ-302`. `projects.list` gives every language of a project `files`, `loc`, `symbols` (the symbols of its files in the newest snapshot) and `tier` (`full` or `basic`, read from the manifest of the installed pack, `null` if there is none). `search.query` takes a project id and a text and returns at most 50 hits of the newest scan, best first, each with kind, qualified name, file, the enclosing symbol and the `project` and `project_name` it belongs to, `files` (at most 10 files whose path matches the text, best first: `path`, `loc`, `first_type` and the project; only files that declare a type) and `entries`, the number of symbols the scan holds (`null` before the first scan); a project without a scan or an empty text gives empty lists. With `all_projects: true` it searches the newest scan of every registered project (`project` is then ignored; projects without a scan are skipped), and each project gets a share of the 50 hits, at least 5. `explorer.source` takes a project id and a symbol id (type or member) and returns the lines of its declaration as they are in the project folder now (`path`, `first_line`, `last_line`, `lines`, `truncated` after 400 lines, `available`) and `spans`: the places in those lines where a symbol is named (`line` counted from 0 within `lines`, `start` and `end` in UTF-16 units, `symbol`), taken from the one-line references of the scan; a place that does not fit its line, because the file changed since the scan, is left out; at most 4000. It needs `read_source` and the token (ADR 0035); a Git project answers `available: false` without lines; a file that is gone, outside the project folder or not a file is `SRC-201`, a file over 4 MiB `SRC-501`. `graph.layers` takes a project id and an optional `level` (`layers`, the default, `namespaces` or `types`, see `docs/graph-layout.md`) and, for the level `namespaces`, an optional `depth` (merge the namespaces into their first `depth` segments; 0 or left out keeps them all) and returns the dependency map of its newest snapshot as a picture: `boxes` (one per layer or, on the level `namespaces`, per namespace, with `name`, `x`, `y`, `width`, `height`, `rank`, `order`, `layer` and `types`), `links` (`from`, `to`, `count`, `violates_layering`, `in_cycle`), `bands` (the stripe of every layer row) and the size of the picture (`width`, `height`). The layers keep the order of the project's `layers` setting, outer layers first, one row each (ADR 0031); a layer that only the scan's edges name is added after them. On the level `types` the input needs `focus`, the symbol id of a type: the answer has three rows of boxes (the types that use the focus on top, the focus in the middle, the types it uses below; at most 12 per side, the rest is counted in `focus.users_more` and `focus.used_more`), each with `symbol`, links from the users to the focus and from the focus to what it uses, counted by references; references inside the type are left out, and `bands` is empty. A missing focus or a symbol that is no type is `MCP-202`. A project without a scan or without layers gives an empty picture (`snapshot: null` before the first scan). The positions come from the layered layout in Rust (`docs/graph-layout.md`); spacing and box size are the `[graph]` settings. `usages.query` takes a project id, a symbol id, `way` (`both`, `incoming` or `outgoing`), `depth` (0 means as deep as `mcp.max_depth` allows, larger values are cut to it) and `include_tests`, and returns the symbol, the `incoming` and `outgoing` walks (at most 500 hits each; `null` for a direction that was not asked), a `summary` of the direct usages, the `impact` of a change (symbols reached, layers, public interfaces) and `level2`. Every hit carries `verified`: `true` only if level 2 produced it (an indexer of ADR 0033 ran, with the owner's confirmation, and checked its file); `summary` counts verified and unchecked hits apart, `probable` counts the unchecked ones that level 1 itself is unsure about, and `level2` is `"active"` if at least one direct usage of the answer is verified and `"unavailable"` otherwise, which tells the UI that no indexer checked anything here. Hits are sorted verified first. Errors as for `explorer.symbol`: `MCP-202` for an unknown symbol, `MCP-203` without a scan. The command needs only the read right, because it hands out no source text. `usages.code` takes the same input and returns `available` and `lines` (`path`, `line`, `text`): the code line of each distinct place of the first 200 hits of both walks, read from the project folder as it is now, trimmed and cut at 240 characters. It needs `read_source` and the token (ADR 0035); the paths come from the index, never from the caller; a Git project answers `available: false`; a place whose file or line is gone is left out. `status.info` takes nothing and returns `startup_ms` (program start until the server answers, `null` if not measured) and `memory_mb` (physical memory of the process, `null` if the system does not tell), `budgets` and `workers` (threads of the analyze stage: one per core the system offers). `projects.cancel` takes a project id and asks its running scan to stop at the next stage boundary; it answers `{ "cancelled": true }`, or `false` if no scan of the project is running (or it has not started yet). The scan then ends without a snapshot: the stream carries `scan_stopped` with `reason: cancelled`, and the call that started the scan (`projects.add`, `projects.rescan`) answers `PRJ-303`. A relative folder path is refused with `PRJ-101`, so the working folder of the server never decides what is scanned.
- No OpenAPI document and no generated TypeScript client yet (needs `utoipa` and real command types, see ADR 0024).
- The UI is part of the program: `build.rs` of the `codeskimr` crate embeds the files of `web/dist` as they are when the program is built (`npm run build` in `web/` first; without it the program has no UI). A folder `ui.dir` that exists wins over the embedded files, so a UI under development can be tried without rebuilding. The embedded files follow the same path rules as a folder. Build order: `web/` first, then the program; without a built UI the build only warns and the program has no UI (release flow: #192). `codeskimr export` takes the export page the same way: from `ui.dir` if the folder exists, else from the embedded files.
- The bare `codeskimr` starts the server and opens the browser with the launch code (blueprint 10.2); the server keeps running until Ctrl+C, also if no browser could be started. `codeskimr serve` and `codeskimr open` remain for the two steps on their own.
- The launch file and the browser start were written for Windows (`explorer`, access rules through `icacls`) and macOS (`open`) and are built there by CI; the access rules and the opener were not run on a Windows or macOS machine by an agent (issue #104 stays open for that check on the real systems).
- No TLS and no non-loopback binding: that is the team server's server mode (ADR 0019).
- Open in #88 and #269: a command id is no secret (unknown id gives `API-201`, a known one without the right `AUTH-401`), which has to be compared with S-06 for the team stage; two first starts at the same moment can each create a token (the later one wins, the earlier process then holds a token that does not match; restart it).
- `serve` needs a usable keystore. On a headless Linux without a Secret Service it stops with `SEC-601`.
- Events are not filtered per principal; in single-user mode there is only the local owner.

- `projects.tools` (scan right, not read only) takes a project id, runs the tool check (`docs/tools-check.md`), stores it and returns the `ToolsView`. `projects.list` rows carry `tools` (the stored report, `null` if never checked) and `projects.add` and `projects.rescan` answer with `tools` of the scan they ran.
