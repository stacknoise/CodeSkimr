# 0072 – Level 2 runs with scans from the UI, and every scan leaves a report of its level

Status: proposed (decision of the product owner Anton on a decision card, 2026-11-18, issue #540; only Anton sets `accepted`)

## Context

ADR 0033 lets only the scan of the command line start indexers; `rescan` through MCP or the UI is level 1 only (addendum "Who starts indexers"). ADR 0071 gave the projects screen a switch for the consent, and the browser can now see whether a project is "on". Anton's test of the stage 2 scan showed two gaps:

1. The switch says "on", but the scan in the browser still never runs level 2. The owner has to go back to the terminal (`codeskimr scan`) to get verified references. He decided: a scan from the UI (`projects.add`, `projects.rescan`) runs level 2 when `[level2] enabled` is set in the user configuration and the project is confirmed, with the same checks as the scan of the command line (`SEC-301`, `SEC-403`). Never for MCP, never on the team server, only for the local owner.
2. Nobody can see at which level the last scan ran. The text "no indexer set up" on the accuracy card was misleading (PR #541 corrects the wording), because the screens have no stored result of the second pass: `Level2Result` lives only in the summary of the scan that just ran (issue #540).

Measured on a private C# project: 124 s for level 2 on 328 files. Today `projects.add` and `projects.rescan` are commands that return when the scan has ended, so the browser would wait minutes inside one HTTP request.

## Options considered

- **A. Run level 2 inside the command and let the request wait.** Simple, but a request of minutes (the server has no timeouts yet, issue #88; `API-503` exists), no progress, no cancel except `projects.cancel` which then lands on a request that is still open, and the page looks frozen. Rejected.
- **B. Level 1 answers first, level 2 continues in the background (chosen).** Level 1 is complete and usable before level 2 starts (ADR 0033, decision 13), so the command can return at that point.
- **C. A separate "Run level 2" button instead of tying it to the scan.** Cleaner in separating the two, but Anton decided that the scan itself runs level 2; a button would be a second way to the same thing.
- **Report storage:** a log line only (not shown anywhere, rejected); the report inside the snapshot (a snapshot is shared between scans, ADR 0032, and a failed level 2 run must not change a finished snapshot, rejected); **its own small tables per project (chosen)**.

## Decision

### Who starts level 2 from the UI

1. **The scan of the UI wants level 2 after level 1.** `projects.add` and `projects.rescan` build their job `with_level2` when the caller is the browser client (decision 2). The command accepts an optional `level2` (default `true`); `false` makes this one scan level 1 only (the screen offers "Stage 1 only" for a quick rescan). The checks are those of `level2::authorize_run`, unchanged: `SEC-403` for a caller without the right to run indexers, `SEC-301` if `[level2] enabled` is missing in the user configuration or the project has no consent for its current source, location and branch. Neither fails the scan: level 1 is stored and the report says "skipped" with that reason (decision 9). `projects.add` of a new project never runs level 2 in practice, because a new source has no consent; the consent is given afterwards (ADR 0071).
2. **A second principal, so that MCP stays level 1 only.** Today `remote_client()` serves both MCP and the HTTP server (ADR 0033 addendum, ADR 0071). This ADR splits it: `browser_client()` is used by `codeskimr serve` (single-user mode) and holds the rights of `remote_client()` plus `RunIndexer`, `RevokeIndexer` and `OpenConfirmation`; `remote_client()` stays for `codeskimr mcp` and **loses** `RevokeIndexer` and `OpenConfirmation` (the tools of MCP never offered them; this makes the test of ADR 0071 decision 4 true without relying on the tool list). `ConfirmIndexer` is held by neither. The team server resolves principals from its credentials and grants none of the three until another ADR says so (ADR 0033, decision 10). A test per principal pins the result (`SEC-403` for MCP and the team server, level 2 for the browser client).
3. **What this changes in the threat picture, said plainly.** In single-user mode the browser client and any holder of the installation token are the same caller. After this ADR such a caller can start the build tools of a project **that the owner has confirmed**, but still cannot confirm anything (ADR 0071) and cannot run an unconfirmed project. Limits: only loopback (ADR 0024), token and permission, one run per project, the cooldown of decision 5, and the limits of ADR 0033 (decision 11). A scan of a Git project fetches new code before level 2 runs; a consent is bound to source, location and branch, not to a commit (ADR 0033 addendum, issue #230), so a pull plus a click runs new build scripts of a repository the owner has confirmed. This is the same as `codeskimr scan` today and is accepted; the confirmation text of `level2 confirm` already says it.

### Running in the background

4. **The command returns after level 1; level 2 continues in a background task.** The answer of `projects.add` and `projects.rescan` gets the field `level2`: `{ "state": "started" }` or `{ "state": "not_started", "reason": "<key>" }` with the reason keys of decision 9. The background task is owned by the composition root (`crates/app`, next to the scan registry in `running.rs`), runs `Level2Pass::run` on the stored snapshot and writes the replacement per file in one transaction per language as before (ADR 0033, decision 13). The project counts as "scanning" until the task has ended: a new scan of the same project is `PRJ-302`, so only one run per project at a time. `MAX_PARALLEL_SCANS` counts the level 2 task like a scan.
5. **Heavy and rate-limited.** An indexer builds the project (minutes, memory, network). Beyond the per-project rule: at most `level2.max_parallel_runs` level 2 runs at the same time over all projects (default 1); a scan that finds the place taken stores level 1 and reports the skip reason `busy`. After a run that the browser started has ended, the next browser-started run of the **same project** waits `level2.ui_cooldown_seconds` (default 60); inside the pause the scan stores level 1 and reports `paused`. Neither is an error and neither is retried by itself. The pause does not apply to the command line; the owner at the terminal is not a click loop.
6. **Progress and cancel.** The event stream (ADR 0024, decision 8) gets two events, ids, counts and labels only, no names or paths: `level2_progressed` (project, language id, stage label `level2_running` or `level2_importing`) and `level2_finished` (project, snapshot id, counts of languages checked, skipped, failed). The projects screen shows "Stage 2 running (C#)" with the existing cancel button; `projects.cancel` while level 2 runs stops the indexer and its process group (ADR 0033, decision 11) and leaves level 1 as it is; the report says `cancelled`. If the server stops during a run, the run is cancelled the same way.
7. **Watch mode stays as ADR 0033 decided.** The first scan of `codeskimr scan --watch` runs level 2; the later scans of watch mode are level 1 only, and nothing runs an indexer on a change of a file: every run takes minutes, uses the network and executes build scripts, so it must be an act of the owner (a new `codeskimr scan`, or a rescan in the browser). The files that changed after the last level 2 run show as stale in the report (`stale` count) and keep level 1 (ADR 0033, decision 13).
8. **A failed, skipped or cancelled run changes nothing it did not touch.** Level 2 replaces references only per file, in one transaction per language, after the hash check. A failure (`RES-5xx` and the other codes of ADR 0033), a cancel or a timeout leaves the references as level 1 and the earlier run stored them; checked results of files that the scan did not re-resolve stay `verified`, files that the scan re-resolved are level 1 until the next run (rows are shared between snapshots, ADR 0032; the implementing package pins this with a test). The report of the failed run replaces the earlier one, and the screen says "the last run failed (code); results of an earlier run may remain for unchanged files".

### The report of the last scan

9. **Stored per project, without paths or secrets.** A migration (the next free number at implementation, after `0016`) adds:
   - `scan_reports`: one row per project: `scanned_at`, `level` (1, or 2 if a level 2 pass checked at least one language in this scan), `origin` (`terminal`, `browser`, `watch`, `mcp`; Anton asked for terminal and browser, the other two are the origins of the level 1 scans that exist anyway). Replaced by every scan.
   - `level2_reports`: one row per project: `run_at`, `origin`, written **only** by a scan that ran the second pass; a level 1 scan of watch mode or MCP does not erase what the last level 2 run said.
   - `level2_languages`: per project and language the `outcome` (`checked`, `skipped`, `failed`), `files` and `stale` counts for `checked`, a `reason` key for `skipped` (`not_permitted`, `not_confirmed`, `tools_unavailable`, `stale`, `cancelled`, `busy`, `paused`) and the registered `code` for `failed`.
   
   Only language ids, counts, keys and error code ids are stored: no path, no tool name or version text (the tool report of ADR 0033, decision 8, keeps those), no output of an indexer, no project name. Rows go with the project (`ON DELETE CASCADE`). A failure to store the report is the new warning `PRJ-502` (`scan_report_not_stored`): the scan and its snapshot are not affected (the scan warnings of migration 0013 carry it).
10. **Where the screens show it.**
    - **Projects (mock 1):** a line per project "Last scan: stage 1 (browser), 14:02" or "Stage 2, checked: C# (328 files)", with "3 files changed since" when `stale` is above 0 or files changed after `run_at`, and "stage 2 failed (code)" with the code. While a run is active the banner of decision 6 replaces it.
    - **Accuracy card (usages, mock 6):** the field `level2` of the usages answer (today `unavailable` or `active`, from the summary) is taken from the stored report and tells apart: checked, checked in part (stale files), skipped with the reason, failed with the code, and "the language has no indexer" (basic tier). The wording follows PR #541.
    - **CLI and MCP:** `codeskimr scan` prints the same lines as today and now stores them; `get_project` of MCP returns the same fields (read only).
11. **API and registry.** `projects.list` carries `last_scan { at, level, origin }` and `level2 { at, origin, languages[] { language, outcome, files?, stale?, reason?, code? } }`. `projects.add` and `projects.rescan` gain the optional input `level2` and the output `level2` of decision 4; no new command is needed because cancel and list exist. The two events of decision 6 are added to the event list of `docs/server.md`. The route and command guards of ADR 0024 are unchanged.

### Errors

12. **One new code:** `PRJ-502` `scan_report_not_stored` (warning, not retryable): the report of the scan could not be stored; the scan itself is stored. Texts in de and en in `locales/*/errors.ftl`, entry in `errors/error-codes.toml` and blueprint appendix A; the number is free on main and in the open pull requests on 2026-11-18 and is in no published release. Everything else reuses codes: `SEC-403` and `SEC-301` (decision 1), `PRJ-302` (a second scan of the project), `PRJ-501` (too many scans), the `RES-5xx` family and the other level 2 codes for `failed`. `busy` and `paused` are skip reasons in the report, not errors.

## Consequences

- **Relation to other ADRs.** ADR 0033: the addendum "Who starts indexers" is replaced for the UI scan (the CLI scan, the first watch scan and the two conditions stay; MCP and later watch scans stay level 1 only). Decisions 9, 10 and 13 and the consent are unchanged. ADR 0071: the browser still never confirms; the statement that the browser starts no indexer is replaced by decision 1 of this ADR; the principal split (decision 2) tightens its decision 4. ADR 0057 (a sandbox) stays the open answer to the residual risk of running build tools.
- Blueprint changes (by the implementing pull requests, label `blueprint-change`): 5.2 (principals and permissions), 9.3 (consent paragraph: UI scan runs level 2 under the same conditions, MCP and later watch scans do not), 10.1 and 10.3 and `docs/server.md` (output field, events), 14 (`level2.max_parallel_runs`, `level2.ui_cooldown_seconds`, user configuration only), the data model and `docs/storage.md` (three tables), 15 (projects screen), 16.1 (level 2 stays outside the budgets, now also in the background), appendix A (`PRJ-502`). `docs/usages.md`, `docs/mcp.md`, `docs/manual/de/indexer.md` and `projekte-und-scan.md`, the English manual, and `locales/` (screen texts in de and en) follow.
- **Mocks** change with the web package and are reviewed by Anton: mock 1 (`Main.dc.html`: the line "Last scan"), mock 18 (`Level2Switch.dc.html`: the banner "Stage 2 running" with cancel, and the option "Stage 1 only") and mock 6 (`Usages.dc.html`: the states of the accuracy card), and the list in `docs/mocks/README.md`.
- **Work packages** (one agent each): (1) domain and application: principals and permissions, `ScanOrigin`, report types and ports, `PRJ-502`; (2) storage: migration and read/write of the three tables; (3) app: background task, registry with `busy`/`paused`, events, `projects.*` input and output; (4) server: events in the stream, no route change; (5) web: projects screen, banner, accuracy card; (6) manual and threat note. Packages 1 and 3 carry `security-sensitive`.
- No new dependency and no `unsafe`.
- Tests that must exist: MCP and team server get `SEC-403` and level 1 only; browser client without consent gets `SEC-301` as a skip and a stored report; a second scan during level 2 gets `PRJ-302`; the cooldown and `busy` produce skips, not errors; cancel during level 2 keeps level 1; a failed run keeps the earlier checked results of untouched files; the report holds no path (a test over the stored text); a level 1 watch scan does not erase the level 2 report; the consent origin test of ADR 0033 stays green (this ADR adds no way to confirm).
- Not decided here: automatic level 2 after file changes, a per-language level 2 button, deleting stored results when the consent is revoked (ADR 0071, decision 10: they stay until the next scan), and a sandbox.
