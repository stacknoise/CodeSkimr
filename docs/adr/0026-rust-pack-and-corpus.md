# 0026 – Rust language pack and the CodeSkimr reference corpus

Status: proposed

*Update: the limit on `impl` blocks (decision 3 and the first item under Limits) is lifted by ADR 0037.*

## Context

WP-65 delivers the full-tier Rust pack (blueprint 8.2). ADR 0011 fixes the reference for Rust: CodeSkimr itself at a pinned commit, with part of the expected values checked by hand. ADR 0016, 0022 and 0023 are the pattern for a language ADR. The `rust` grammar has been a dependency of `codeskimr_parsing` since the parsing engine (WP-23) and is registered in `grammar.rs`, so this package needs no new dependency and no change outside `languages/rust/`, `corpus/rust/` and the tests. The pack format of ADR 0016, 0022 and 0023 is sufficient; nothing is added to it.

## Decision

### 1. Grammar

`tree-sitter-rust` 0.24 (MIT), already compiled in. Extensions: `rs`. The qualified-name separator is `::`, so `analyzer::TreeSitterAnalyzer::new` reads like a Rust path (the file module comes first, like in every pack).

### 2. Reference: CodeSkimr at a pinned commit

`corpus/rust/corpus.toml` pins [stacknoise/CodeSkimr](https://github.com/stacknoise/CodeSkimr) (MIT) at commit `bcc970e90cb99c2d052457f79090a78194dfaa8e`: 147 files of the crates (`crates/**/src`; tests, benchmarks, tools, the web UI and the data folders are skipped), about 15,500 lines. The project is public, so the corpus test fetches it like the other references.

The counts were measured with the pack and checked against an independent count with the `syn` crate (a different parser, same mapping rules, visiting every item including those inside function bodies and in `impl` blocks). Every kind agrees exactly: 147 modules, 150 `mod` items, 182 structs, 32 enums with 127 variants, 18 traits, 34 type aliases, 383 constants, 340 functions, 375 methods and 581 named fields. A hand-checked sample of symbols with visibility and parent and four references (an import, an `implement`, an `override`, a type use) is in the file. Updating the commit is a deliberate change with new expected values.

A pinned commit does not move, so the corpus stays reproducible; it also means the reference is not the current CodeSkimr. That is intended (ADR 0011).

### 3. Mapping

Written down in `languages/rust/language.toml`. Decisions worth knowing:

- `mod` is a `namespace`, `struct` a `struct`, `union` a `union`, `enum` an `enum` with its variants as `enum_member`, `trait` a `trait` (not an `interface`), `type` and associated types `type_alias`, `const` and `static` (also the associated constants of traits and impls) `constant`. Named fields of a struct, a union or an enum variant are `field`s; the fields of a tuple struct are not symbols.
- A function directly in a module, a block or at the top of a file is a `function`, also a local one inside a function body (it counts for itself, like a local function in C#, ADR 0015). A function in an `impl` or a trait is a `method`; there is no constructor kind (`new` is a convention), so no `constructor` is produced. A function without `self` in an `impl` or trait is `static`.
- `impl` blocks are no symbols. A kind is a fact about a declaration and an `impl` declares nothing; making it a symbol would give the type two symbols with the same qualified name. The consequence is that the methods of an `impl` belong to the enclosing module (`analyzer::new`, not `analyzer::TreeSitterAnalyzer::new`), and two `impl` blocks of one module that both have a `new` give two symbols with the same qualified name (the same limit as Go in issue #65).
- Visibility: `pub` is public, `pub(crate)` and `pub(in path)` internal, `pub(super)` protected, `pub(self)` and no keyword private. The query captures the tokens of the modifier (`pub`, `crate`, `super`, `self`, `in`), and `[visibility.keywords]` maps the joined words (`pub crate`). Variants of an enum and members of a trait are public, and so is a function of a trait implementation (`impl Trait for Type`): the head's `for` is captured as a word with the same meaning. Associated types and constants of an `impl` get the default (private) because their `impl` has no symbol.
- Documentation: `///` lines and `/** */` blocks directly above a declaration, attributes (`#[derive(..)]`) may stand between. `//!` and `/*! */` (documentation of a module or crate) are not read; a `////` line counts as a doc line (a known gap of the prefix rule).
- Not symbols: `impl` blocks, parameters, local variables, closures (they count for their function), `use`, macros (`macro_rules!` and their invocations; items generated by a macro are not seen), `extern` blocks, tuple struct fields.
- `metrics.scm` follows ADR 0015: `if` (also `else if` and `if let`), `for`, `while` (also `while let`), `&&` and `||` and every `match` arm count; the wildcard arm `_` does not, also not with a guard (the `&&` of a guard counts); `else`, `loop`, `?`, `let … else` and `unsafe` do not. A call counts as the operator `(`, an index expression as `[`, `?` and `as` as operators.
- `references.scm` is level 1 (blueprint 9.2): calls (`f()`, `x.f()`, `Foo::f()`, with the turbofish), type uses (annotations, fields, return types, generic arguments including the name of a generic type, `Foo { .. }`, bounds), imports (`use` with lists and `as`), a supertrait is `inherit`, `impl Trait for Type` is `implement`, a function of a trait implementation is an `override` of the trait function of that name. `self` and `Self` are the own receiver, `Foo::new()` a receiver named `Foo`; locals, parameters and `let` patterns hide members; a declared type, `Foo::new()` or `Foo { .. }` gives the type of a variable.

### 4. What the pack format does not need

Everything is expressed with the existing vocabulary: visibility words and `for`, `@static`, `doc_prefixes` plus `[doc_block]`, `@doc` on sibling comments. A learning for later packs (it adds to ADR 0022): a parent pattern with a quantified comment and an anchor (`(declaration_list ((comment)* @doc . (x)))`) finds only the first declaration of the list; the packs use `(comment)+ @doc .` with a pattern of their own for the declaration without documentation, and patterns for the visibility and `static` that repeat the symbol capture (the adapter merges the matches of one declaration).

## Limits (follow-up work)

- `impl` blocks are no symbols, so `implement` and the types in the head of an `impl` belong to the module, not to the type, and the resolver cannot yet build the hierarchy from them. A fix needs a change to the engine (a symbol-less container that names its type, for example), which is outside this package (issue).
- Inline `#[cfg(test)] mod tests` blocks are normal symbols (a namespace and its functions); the `test_patterns` of the pack only match test files and folders.
- Names with generics only reach the resolver by their simple name; paths with several segments (`a::b::f()`) report the last segment with the one in front as receiver.
- Macros: items generated by `macro_rules!` and the calls inside macro arguments (`format!("{}", f())`) are not seen.

## Consequences

- No file outside `languages/rust/`, `corpus/rust/`, `docs/` and the tests changes; the parsing adapter is untouched.
- The corpus test now walks four references (C#, TypeScript, Python, Rust).
- `tests/rust_metrics.rs` is the golden test of `metrics.scm`, with the helpers shared with the other languages.
