# Level 2 import: SCIP indexes (ADR 0033, package 5)

`crates/adapters/scip` (`codeskimr_scip`) turns a SCIP index into level 2 references. The mapping is a pure function over domain types; `ScipImporter` implements the `ReferenceImporter` port of the application layer, which the second pass of the scan (below) calls. The crate depends on `application`, `domain` and `codes`.

## Decoder

`decode_index(bytes, max_index_bytes)` and `read_index(path, max_index_bytes)` read the Protobuf format of Sourcegraph's `scip.proto` with a small hand-written reader (`wire.rs`): no `protoc`, no generated code, no new dependency. It reads only `Index.metadata.project_root`, `Document.relative_path` and `position_encoding`, and `Occurrence.range`, `symbol` and `symbol_roles`; every other field is skipped.

The index is untrusted input (ADR 0033 decision 4):

- The size is checked before the file is read, and the read stops one byte past `level2.max_index_bytes` (default 256 MiB). A larger index fails with `RES-501`.
- Nothing is allocated for input that has not been checked: strings are length-checked (paths 4 KiB, symbols 64 KiB) before they are copied, ranges hold at most four numbers, skipped groups may nest 8 deep, varints are strict (at most ten bytes, no bits beyond 64), and a SCIP symbol that occurs many times is stored once.
- The number of things is limited too, because a small file grows in memory: at most 1,000,000 documents, 16,000,000 occurrences and 4,000,000 distinct symbols (`consts.rs`). An occurrence takes about 13 bytes in the index and 24 in memory (a factor of about 2), and the text of every distinct symbol is held twice (list and lookup table) plus its parsed descriptor in the import, so budget roughly two to three times the index size for the decoded index and the import together. `read_index` reserves the file size once instead of growing the buffer.
- A bad range fails the index even on an occurrence without a symbol, which would be dropped anyway.
- Document paths are cleaned lexically (`/` as separator, no `.` and empty components) and refused if they are empty, start with a separator, name a drive or hold a `..` component (blueprint S-05). The import never opens a file by such a path; it only compares it with the paths of the snapshot.
- Truncated, malformed or out-of-range input is `RES-101`. The decoder does not panic; a test feeds it random and damaged bytes.

Columns of an occurrence are in the unit the document states (`PositionEncoding`, kept on the decoded document); scip-dotnet and scip-typescript count UTF-16 code units, the parsing adapter counts UTF-8 bytes. `convert_columns` turns the columns of a document that is not UTF-8 into byte columns before the mapping, using the lines of the file (`SourceText`, which never follows a link out of the project). A column inside a surrogate pair stands for the next character. If the text of a file cannot be read, or a column lies behind the end of its line, the occurrence keeps its columns. `read_index` refuses a link in place of the index file (issue #217).

## Mapping and replacing

`import_references(index, snapshot, min_mapped)` is a pure function. The snapshot is the files, symbols and references of one language.

1. **Definitions.** An occurrence with the definition bit (`symbol_roles & 1`) is mapped onto the smallest symbol of the same file whose span contains the position and whose name is the name of the last descriptor of the SCIP symbol (descriptor syntax of `scip.proto`: suffixes `/` `#` `.` `:` `!`, methods `name(+n).`, `[type parameter]`, `(parameter)`, backtick names with `` for a backtick). A qualified name in one backtick name matches by its last segment (`System.IDisposable.Dispose`), and `.ctor`, `<init>` and `<constructor>` match a project constructor, which is named like its type. Among symbols with the same span the one whose kind fits the descriptor wins, then the lowest id. `display_name` is not used.
2. **Overloads.** SCIP tells overloads apart and so does CodeSkimr (one symbol per declaration, same qualified name), so each overload follows from the position of its definition.
3. **Partial classes.** One SCIP symbol can have several definitions, one per file. The occurrence becomes one reference per CodeSkimr symbol of the type (`mapped` counts the occurrence once).
4. **References.** Every other occurrence of a mapped symbol becomes a reference from the smallest symbol of the file that contains the place to the mapped symbol, `certain` and `verified = true`. The kind is the kind of the level 1 reference at the same place (same start, else a span that holds the occurrence) if there is one, else by the target: callable is `call`, type is `type_use`, anything else `read`. The same place and pair is stored once. New ids follow the highest id of the input.
5. **Replacing per file.** For every file that an index document names (after cleaning the path), all level 1 references of the file are replaced. Files without an index document keep level 1.
6. **What is not a reference.** Local symbols (`local N`), parameters, type parameters, meta and macro descriptors, and namespaces without a definition are ignored. Occurrences of symbols the index does not define are library symbols and are dropped (`library`). Occurrences of symbols the index defines but that match no snapshot symbol (code generated by a macro, a name the language pack does not report) or that lie in no symbol are dropped as `unmapped`.
7. **Threshold.** The share `mapped / (mapped + unmapped)` must reach `level2.min_mapped` (default 0.5); library occurrences do not count, because most occurrences of a real project point into libraries (measured below: 50 %). An index that covers no file fails as well, and so does one whose covered documents hold uses of which none mapped (for example an indexer that never marks definitions). All fail with `RES-302`, and the caller keeps level 1. An occurrence that lies in no symbol of its file has no origin and counts as `unmapped`.
8. **`Self` in Rust.** rust-analyzer does not write `Self` as a use of the type but of its impl block: `.../impl#[Type]` (and `impl#[Type][Trait]` for a trait implementation), a symbol without a definition. Generic arguments are cut off (`Job<Queued>` is `Job`); a path is kept. Only what is certain maps to the type: (a) a bare name is the type of the same module (the text before `impl#` plus `Type#`); (b) a path (`crate::a::Type`, `io::Error`) maps only to the one project type of that name that lies in exactly those modules (path from `crate`) or whose modules end with the path, so `io::Error` is not taken for a project type `Error`; (c) a bare name from another module maps if the same document names the type in the header of the block, that is, exactly one type symbol of that name occurs in the document and it is a project type. A library type of the same name, two project types or no occurrence map nothing; the occurrence is ignored, not guessed. `self::` and `super::` paths and forms such as `&Type`, `[T; N]`, `dyn Trait` are not read. The kind is the kind of the level 1 reference at the place, else `type_use`. A symbol that starts with `local ` is a local symbol whatever its text says.
9. **Methods of trait implementations.** SCIP gives such a method the symbol `impl#[Type][Trait]name().` and marks its definition. For every such definition the import adds an `override` reference from the method to the method of the trait, `certain` and `verified`, if exactly one **trait of the project** has that name and defines the method (the owner must be a trait, not a struct or enum), and, if the impl symbol gives a path (`crate::api::Trait`, `std::hash::Hash`), the trait lies in those modules. A trait of a library, an ambiguous name (two traits of that name, no path) or a path that fits no project trait gives no reference. A bare trait name is taken as the project trait of that name; a library trait with the same bare name as a project trait cannot be told apart from it, which is the known gap of this rule. Level 1 had this reference too, at the start of the function; because all references of a covered file are replaced, level 2 has to produce it itself. Not read from the index: the `Relationship` entries of `SymbolInformation` (issue #241 lists reading them as the cleaner way). The header of the symbol (package name) is skipped before the impl form is looked for.
10. **Functions that start behind their name** (`const isObj = (v) => ...`; TypeScript). The span of the project symbol starts at the function, not at the name, so no span contains the definition. If none does, the symbol of that name that starts on the same line behind the definition counts, if there is exactly one; two are not told apart. The indexer calls such a function a variable (`isObj.`), so the kind is not compared.
11. **Local functions** (any language whose indexer gives local functions a local symbol; measured for TypeScript). A function declared inside another function gets a local symbol (`local 12`), which has no name. `convert_columns` reads the name from the text of its definition (one line, at most 256 bytes, in UTF-8 columns; where the text is not available the symbol stays without a name and maps nothing). The definition is matched to a project function by place and name: the function starts on the line of the definition behind it, the definition is the last one on that line in front of the function's start, and its text is exactly the name of the function (not only as long). A definition that two functions claim is dropped. Local symbols are looked up per document; every other local symbol (parameters, variables) stays ignored. Lookups use an index by file, line and name, so a line with many symbols costs a binary search per lookup; looking for the declaration of an overload head weighs at most 16 symbols of one name per line, else nothing is mapped.
12. **Getters, setters and overloads.** scip-typescript names accessors `<get>size` and `<set>size`; the prefix is dropped before the name is compared, so both are the one property of the project. scip-python has one symbol for all overloads of a function and defines it at the first one; the heads of the others and the implementation appear as plain occurrences. An occurrence that stands on the declaration line of a function of the same name, in the same file and the same parent as a target of its symbol (and is the first of that symbol on that line) is the head of that function: the function becomes another target of the symbol, so uses go to every overload, and the occurrence is no use (only for that symbol: another symbol's occurrence at the same place stays a use). A symbol takes at most 64 such heads, and nothing is looked up for a symbol without a target. A function that is already the target of a symbol has its own symbol and is no head (C#: `IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();` on one line: the call stays a use of the public method).
13. **Constructor calls are uses of their type.** scip-java writes `new Gson(this)` as a use of the constructor `Gson#<init>().` at the name of the class; the class gets no use from the index. For a reference to a constructor of the project, the import adds a reference to the type of the constructor (its parent in the snapshot) if level 1 has a reference to that type at the same start. `this(...)` and `super(...)` stand on a keyword, level 1 has no reference to the type there, and so none is added. The kind is that of the level 1 reference. Where the index writes no constructor at all (`new X(...)` in scip-dotnet) there is nothing to map (issue #259); for Java see point 14.

14. **Java: what the text adds** (`crates/adapters/scip/src/javatext.rs`, `src/mapping/implicit.rs`; only files ending in `.java`, only where the text of the file is available and the columns are bytes; otherwise the index is taken as it is). The scanner is small and gives up on anything it does not expect (too long, unbalanced, a string that does not end), and then nothing is marked.
    - *Import lines are no uses.* The occurrences on the lines of an `import` declaration (from the keyword to the semicolon, also over several lines) are dropped before the mapping; level 1 does not count them either (issue #250 is decided for Java only; TypeScript and Python are untouched).
    - *Implicit `super()`.* A constructor whose body does not start with `this(...)` or `super(...)`, and the default constructor of a class without one, call the constructor of the direct superclass without arguments. scip-java writes no occurrence for that call; javac counts it at the opening brace of the body (the name of the class for a default constructor). The import adds a `call` reference there if the superclass is the one that stands in the `extends` of the class (the occurrence of a class symbol where level 1 reads an inheritance at the same place), and that superclass has exactly one declared constructor without parameters, or, if it has none, exactly one declared constructor with only a varargs parameter (the rule of the language). The parameter lists come from the text. No such constructor, two candidates, a superclass of a library or an overload that cannot be told apart: nothing is marked.
    - *Anonymous subclasses.* `new X<T>(args) { ... }` is written as a use of the type only. javac counts the call of the constructor at the opening brace of the body. The import adds it if `X` declares exactly one constructor.
    - *Constructors without symbol.* `new X()` of a class without a declared constructor is written as a use of `X#<init>().`, which the project has no symbol for. It is a use of the class `X` now (and so is the constant of an enum without a body: javac reads it as the creation of the enum); before it was dropped as unmapped.
    - *Enum constants with a body* (`NAME(args) { ... }`) are a use of their enum at the name of the constant.
    - *Left out:* members of anonymous classes (a local symbol, no name to look up, issue #366) and anything the text does not settle.
    - *Limits of the text reader.* It reads strings, characters, text blocks (`"""`), comments and groups of brackets, and nothing else of the grammar. A scan stops after 8192 characters; all scans of a file together may read 16 times its size (at least 8192 characters); a file that needs more is read only in part and nothing is marked in it (its import lines are still dropped). It does not follow a type name written with a path (`new a.b.X() { }`), a `new` on the line before its type, generic constructors or a statement before `this(...)` or `super(...)` (the language does not allow one). `<` and `>` count as brackets inside the parameter list, so a comparison in an annotation argument can make a constructor unreadable; it then stays unmarked. A qualified call `outer.super(...)` as first statement is an explicit call.

`ImportStats` has `mapped`, `library`, `unmapped`, `ignored`, `files_replaced` and `files_unmatched` (documents without a snapshot file, for example generated code that is not scanned).

## Symbols that level 2 creates (ADR 0055)

Level 1 cannot see what a `macro_rules!` call generates (`id_type!(SymbolId)`, `labeled_enum! { SymbolKind { ... } }`). The index knows these definitions. For the kinds a language pack lists, level 2 now creates a symbol with `origin = index` and maps the uses to it. Rust only for now.

- **Kinds.** The pack names them in `[indexer.symbol_kinds]` (SCIP kind name to symbol kind; Rust: `Struct`, `Enum`, `EnumMember`, `Trait`, `TypeAlias`). It sits in the `[indexer]` table, next to the rest of what the indexer needs per language. The pack's top-level `separator` joins the qualified names.
- **Which definitions.** A definition (an occurrence with the definition role) whose `SymbolInformation` has a listed kind, whose file the index covers, and for which level 1 has no symbol of the same name and line. `macro_rules!` definitions are not created.
- **Parent.** In this order: the created symbol that the descriptor path names (same file); the level 1 symbol that the descriptor path names; the innermost level 1 symbol around the definition; otherwise the candidate is dropped. The parent is always in the same file. The qualified name is the parent's plus the separator plus the display name. The span is the `enclosing_range` of the occurrence when it contains the range, else the range; signature and documentation come from the index (bounded: oversized texts are dropped, the total is limited to 32 MiB).
- **Lifetime.** Created symbols belong to their file. `Level2Replacement` (formerly `ReferenceReplacement`; the port method is `replace_level2`) carries files, symbols and references and replaces them in one transaction. A rescan that changes the file removes its created symbols and the references to or from them; the next level 2 pass creates them again. Level 1 ignores symbols of origin index: they are not in the resolver table and not in the carry maps, so references to them of changed files are dropped and not re-resolved by name.
- **No metrics.** Created symbols have no metric rows, no fingerprints and no rule checks; those apply to level 1 symbols only.
- **Ids.** The importer numbers created symbols from the largest id plus one; the pass renumbers them through the shared `IdSequence` (symbols and references, with the parent and the ends of the references mapped along).
- **Limit.** `level2.max_created_symbols` (default 100000) bounds the number of created symbols. If more would be created, the whole import fails with `RES-303` and nothing is replaced.
- **`verified`.** Stays on the reference as for any level 2 reference.
- **Visible in.** `origin` is a field of the symbol in the API and in the MCP answer of `get_symbol`; the UI shows no marker.

Measured on the CodeSkimr corpus (index of 2026-11-14, 8792 project uses before): 72 symbols are created (16 struct, 7 enum, 49 enum member). Uses without a level 1 symbol fall from 1498 (17.0 %) to 659 of 8805 (7.5 %). Of the 1498, 839 uses now map to 69 of the 72 created symbols and 13 more map (impl `Self`). The remaining 659 are 603 uses of module paths (namespace descriptors such as `crate/` or `sql/`; modules are not created, out of scope of the ADR) and 56 definitions in the skipped folders of the corpus. The acceptance figure "under 1 %" of the ADR is therefore not reached; the follow-up is module paths.

## Limits

- The enclosing-symbol search is linear in the symbols of a file for every occurrence, so very large or single-line files are quadratic (issue #220).
- The index decides which files are covered; a file that the indexer did not see keeps its level 1 references.
- Created symbols need the definition in the same file as the parent; a candidate without a parent is dropped.
- Columns are not converted between encodings (see above, issue #217).

## The second pass of the scan

After level 1 is stored, `Level2Pass` (application layer, `level2/pass.rs`) runs once per distinct indexer name. Languages that name the same indexer (TypeScript, JavaScript and TSX; Java and Kotlin) share one run and get one report each.

For each indexer, in this order: `authorize_run` (permission, enabled in the user configuration or the project record, confirmed); `IndexRunner::check` (tools installed in a usable version); `IndexRunner::run`; then a hash check of every file of the languages against the disk, which happens **after** the run because the run may take minutes. Files whose content changed keep level 1 and are counted as `stale`; if all changed, nothing is imported. The importer maps the index onto the files that passed, and `SnapshotStore::replace_level2` replaces the references of exactly those files in one transaction; the new references get ids the pass reserved from the shared id sequence, so they cannot collide with rows of other snapshots; the transaction also updates the totals, rebuilds the read models and calculates the coupling of the newest snapshot again (ADR 0037).

Whatever goes wrong, the scan has finished and level 1 stays: the pass never fails the scan, a cancel kills the process group and leaves the references as they were, and the report names the reason per language (not permitted, not confirmed, tools missing, stale, cancelled, or the error code). `codeskimr scan` prints one line per language ("Level 2: ... checked" or "skipped (reason)"), `--json` carries the same data.

Rows are shared between snapshots that carry a file unchanged (ADR 0032). `replace_level2` therefore treats every snapshot that holds a replaced file alike: the new references are visible from the oldest snapshot that holds the file, and the totals and read models (usage counts, layer graph, search) of all of them are built again, in the same transaction. Only the newest snapshot of a project can be asked for a replacement. A test with two snapshots that share a file pins this. Coupling is the exception: it belongs to one snapshot (ADR 0037), so only the newest snapshot gets it calculated again; older snapshots keep their level 1 figures.

A file that is not valid UTF-8 is read lossily by `FolderText` (invalid bytes become a three-byte character), so byte columns behind such a byte can be off; the hash check does not help there. An occurrence that cannot be placed in the text of its line is dropped, not kept with a wrong column. `SnapshotCreated` is published as soon as level 1 is stored and once more after level 2 if the totals changed, so UI, MCP and watch mode do not wait for the indexers. After its run, every indexer group hashes only its own files once more (`FileDiscovery::unchanged_files`, `docs/level2-runner.md`), not the whole project. Watch mode runs level 2 with its first scan only; later scans of the session are level 1 (`Job::without_level2`).

## Running time on large single files (issue #220)

The symbols of a file and the level 1 references of a line are searched through an interval index (`crates/adapters/scip/src/interval.rs`, sorted by start, each node knows the largest end below it), not by a scan over all of them for every occurrence, and the targets of an occurrence are shared instead of copied. A minified or generated file with thousands of symbols and occurrences on one line therefore imports in about linear time. Measured with `cargo test --release -p codeskimr_scip --test scip scale -- --nocapture` (one file, one line, N methods, each used once; before and after): 2000 methods 38 ms and 5 ms, 4000 methods 147 ms and 12 ms, 8000 methods 557 ms and 22 ms, 20000 methods 4.2 s and 61 ms. The test `a_file_with_thousands_of_symbols_on_one_line_imports_in_time` keeps it that way.
