# Acceptance report M4 (WP-54)

Status of 2026-11-13, commit `91d64da` (main at the start of the run, after WP-51; later commits only add other packages). The criteria are those of blueprint 19 for milestone M4: screens 3 (dependencies), 5 (scan and performance) and 6 (usages) match the mocks, graph layout under 50 ms, usages at depth 2 under 20 ms, and the jump from the explorer to the usages. The accuracy of the usages is not part of this report (WP-67, see `docs/accuracy.md`).

**Machine:** Linux container, 4 vCPU, release build. As in the M1/M2 report, absolute times are indicative; blueprint 16.1 names a mid-range laptop. The one budget that fails here fails by a factor of up to 3.8 (measured 17 to 76 ms against 20 ms), which the machine alone does not explain.

## Budgets

Measured with `tools/acceptance/m4-measure.mjs`: it starts the end-to-end server of the app (release build), scans a folder (CodeSkimr itself: 521 files, 7,863 symbols, 31,936 references, scan 0.6 s) and calls the REST commands with timing in the client, so every number includes the HTTP round trip on the loopback address.

### Graph layout (`graph.layers`)

| Measurement | Result |
|---|---|
| Benchmark `graph_layout/nodes_200` (domain layout) | 0.46 ms (0.45 to 0.46) |
| Benchmark `graph_layout/nodes_1000` | 2.6 ms |
| Benchmark `graph_layers/layers_200` | 0.40 ms |
| Command `graph.layers`, CodeSkimr (6 layers, 25 links), 50 calls | median 0.92 ms, p95 1.50 ms, max 2.19 ms |
| Same, second run, 30 calls | median 1.33 ms, p95 2.16 ms |

Limits of this result: the real map has only the layers of the project (6 boxes here). The case "up to 200 nodes" is covered by the benchmark only; there is no command for the namespace or type level yet (#163). Drawing on the canvas in the browser is not measured; blueprint 16.1 budgets the layout.

### Usages query at depth 2 (`usages.query`)

| Incoming usages of the symbol | Symbols | Median (first call) | p95 | Max |
|---|---|---|---|---|
| 0 to 9 | 218 | 1.6 ms | 4.0 ms | 33.8 ms |
| 10 to 99 | 119 | 6.7 ms | 10.6 ms | 13.2 ms |
| 100 to 999 | 61 | 17.0 ms | 29.2 ms | 45.6 ms |
| 1,000 and more | 2 | 76 ms | | |

The 400 symbols come from ten searches (`new`, `error`, `path` and so on); each was queried once with `way = both`, `depth = 2`, tests included. The five symbols with the most usages (2,275, 1,147, 595 and two smaller ones) were then queried 30 to 50 times: medians 24, 34, 45, 54 and 60 ms (p95 up to 80 ms). For the five large symbols the repeated medians (24 to 60 ms) are below the single first call of the two largest ones (76 ms, n = 2); the single calls include a cold cache and are less reliable.

Where the time goes (largest symbol, 30 calls each): `both` at depth 1: 61 ms; `incoming` at depth 1: 58 ms; `incoming` at depth 2: 61 ms; `outgoing` at depth 2: 35 ms. Depth makes no difference, so the walk through the index (2.1 ms in the benchmark) is not the cost. The likely cost is the lookup of names, kinds, layers and paths of up to 500 entries per direction, which issue #83 describes; this is a hypothesis from the measurements (no profile was taken), to be confirmed in #165. The benchmark does not cover this part, so CI cannot see the failure. The medians of the buckets below 100 usages are well under 20 ms (the 0 to 9 bucket has single outliers up to 34 ms), the median of the bucket 100 to 999 is just under it (17 ms) with a p95 of 29 ms, and the largest symbols are far over. Hub symbols are exactly the case where the impact analysis matters. Issue #165.

## Comparison with the mocks

The mock sources in `docs/mocks/` are written for a design canvas whose runtime is not in the repository, and the published canvas is private. `tools/acceptance/render-mock.mjs` fills the small template language of a mock (`{{name}}`, `<sc-for>`) from the mock's own data function and renders it with Chromium at 1440 × 900. `tools/acceptance/m4-screens.mjs` takes the screenshots of the real UI over the end-to-end server in the theme Hell and the language German, as the mocks are drawn (blueprint 15.1). The mocks hold sample data, so only structure, proportions, labels and behaviour are compared, not the content. The comparison is by eye plus the inline values of the mocks; a pixel diff would be meaningless with different data. Fonts of the mock render may differ slightly (the mock loads them from a web font service).

Images are in `docs/acceptance/m4/`: `mock-*.png` is the mock, `real-*.png` the application.

## Repeat

```sh
cd web && npm ci && npm run build && cd ..
node tools/acceptance/m4-measure.mjs <project-folder> 50          # budgets
CODESKIMR_CHROMIUM=<chromium> node tools/acceptance/render-mock.mjs Graph mock-graph.png   # one mock (Graph, Scan, Usages)
CODESKIMR_CHROMIUM=<chromium> node tools/acceptance/m4-screens.mjs <project-folder> <out> hell de
cargo bench -p codeskimr_bench --bench graph_layout --bench usages
```

`m4-measure.mjs` and `m4-screens.mjs` start the end-to-end server with `cargo test --release` (a few minutes for the first build) and write nothing into the project folder. They need a Chromium for the screenshots (`CODESKIMR_CHROMIUM`, as for the e2e tests of `web/`). `m4-screens.mjs` names its files `<screen>-<theme>.png`; the report's `real-*.png` are `graph-selected`, `scan`, `usages` and `usages-scrolled` renamed (it selects a type by quick search, default `ReverseIndex`, set `M4_TYPE` for another project). The scan of CodeSkimr took 0.6 s here against 1.6 s in the M1/M2 report because incremental work and the faster parse since then are included; this was not analysed further. `m4-screens.mjs` clicks through a project with layers and a type named by `M4_TYPE`, so it needs a project that has one. The scripts are for acceptance runs; CI does not run them.

## Verdict

M4 cannot be accepted yet. Met: the graph layout budget (far below 50 ms) and the jump from the explorer to the usages. Not met: the usages budget at the command level (#165; the walk itself is fast, the lookup of the entries probably is not) and the match with the mocks (frame, graph bands and namespace level, performance figures, scan and usages details; #163, #166 to #169, #157, #158). Everything listed works and is covered by tests; what is missing is detail against the mock and the namespace level of the map. After #165 is fixed the measurement is repeated with `m4-measure.mjs`; the mock comparison is repeated after the UI issues.
