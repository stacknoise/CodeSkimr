# Acceptance report M3 (WP-49)

Second run of 2026-11-14, commit `0653800` (main after #300). The first run (2026-11-13, commit `3a07eb4`, after WP-43) found the UI not embedded in the binary, many content details of the screens open and no benchmark guarding the search budget. Since then #103 (embedding), #167, #171, #178, #158 (top bar, keys, search and settings details), #105 (settings kept on the server) and #144 (search benchmark in CI) are closed. The criteria are those of blueprint 19 for milestone M3: the caller-identity seam (WP-59), the axum server with the embedded UI, screens 1 (projects), 2 (explorer), 4 (quick search) and 13 (settings with themes), the status bar with live measurements and the de/en switch; and the acceptance criteria: screens match the mocks (visual review), the keyboard paths of 15.4 work, the budgets for search and type switch are met, screen 13 offers Hell, Petrol and Dunkel with live preview and stores and applies the choice, and every screen passes the visual test in all three themes and the contrast check of 15.3.

**Machine:** Linux container, 4 vCPU, release build. As in the M1/M2 and M4 reports, absolute times are indicative; blueprint 16.1 names a mid-range laptop. The measured project is CodeSkimr itself, larger than in the first run (703 files, 11,800 symbols, 145,479 references, 72,129 lines, first scan 1.4 s), so the figures are not comparable one to one. Both budgets are still met by a factor of 1.6 or more, so the machine does not change the verdict.

Legend: ✅ met · ❌ not met (issue linked) · ◐ partly met

## Budgets

Measured with `tools/acceptance/m3-measure.mjs`: it starts the end-to-end server of the app (release build), scans a folder (CodeSkimr itself: 703 files, 11,800 symbols, 145,479 references, scan 1.4 s) and calls the REST commands with timing in the client, so every number includes the HTTP round trip on the loopback address.

### Quick search per keystroke (`search.query`)

Every prefix of six names (`ReverseIndex`, `Scanner`, `Config`, `storage`, `resolve`, `Symbol`) was sent as one call, as typed in the overlay, repeated five times.

| Measurement                         | Result                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------ |
| All 225 calls                       | median 3.92 ms, p95 6.00 ms, max 9.62 ms                                                         |
| Slowest prefixes of the first round | `R` 9.3 ms, `Re` 7.9 ms, `S` 7.4 ms, `r` 6.0 ms, `s` 5.9 ms (one-letter prefixes return 50 hits) |

Limits: this is the command, not the key press. Drawing the 50 rows (the list is virtualised) and the preview in the browser is not measured. The benchmark in CI that guards this budget now exists (#144, #294).

### Switch the selected type (`explorer.symbol`)

| Measurement                                           | Result                                   |
| ----------------------------------------------------- | ---------------------------------------- |
| First call for each of 45 types                       | median 3.98 ms, p95 6.73 ms, max 11.04 ms |
| Five largest of them (6 to 15 members), 50 calls each | median 3.91 ms, p95 5.50 ms, max 10.64 ms |
| `explorer.outline` (the whole tree, not a budget)     | median 8.1 ms, p95 11.4 ms               |

Limits: the budget is one frame (16 ms) in the browser. The command leaves about 14 ms for rendering the details and the table; the 45 probed types come from a few searches and have at most 15 members, so a type with hundreds of members is not covered. The rendering part is not measured here (the status bar of the mock shows a "selection 3 ms" figure that the application does not have).

## Comparison with the mocks

Method as in the M4 report: `tools/acceptance/render-mock.mjs` renders a mock at 1440 × 900, `tools/acceptance/m3-screens.mjs` takes the real screens over the end-to-end server in German for each theme. Images are in `docs/acceptance/m3/`: `mock-*.png` is the mock, `real-<screen>-<theme>.png` the application. The mocks hold sample data, so structure, proportions, labels and behaviour are compared, not content. Mocks 1, 2 and 4 are drawn in Hell, so their colours follow the active theme (blueprint 15.3); mock 13 is drawn in Petrol. The sizes of the frame, the columns, the dialog and its rows are also checked automatically (see criterion 3).

## Repeat

```sh
cd web && npm ci && npm run build && cd ..
node tools/acceptance/m3-measure.mjs <project-folder> 50                  # budgets
CODESKIMR_CHROMIUM=<chromium> node tools/acceptance/render-mock.mjs Main mock-projects.png   # Main, Explorer, Palette, Themes
CODESKIMR_CHROMIUM=<chromium> node tools/acceptance/m3-screens.mjs <project-folder> <out> de  # all screens, all themes
cargo run --locked -p codeskimr_codegen                                    # contrast check of 15.3
cd web && CODESKIMR_CHROMIUM=<chromium> npm run e2e                        # mock sizes and keyboard paths
```

`m3-measure.mjs` and `m3-screens.mjs` start the end-to-end server with `cargo test --release` (a few minutes for the first build) and write nothing into the project folder. `m3-screens.mjs` opens the type `ReverseIndex` (set `M3_TYPE` for another project); it needs a project that has this type. The scripts are for acceptance runs; CI does not run them.

## Verdict

M3 can be accepted, with two named leftovers. Met: the caller-identity seam, the embedded UI, the keyboard paths (39 of 39 end-to-end tests green), both budgets (search p95 6.0 ms against 10 ms, type switch p95 5.5 ms on the server against 16 ms, on a project twice the size of the first run), the theme screen with live preview and storing, the contrast check, the status bar and the language switch. Partly met: criterion 3 (the remaining deviations from the mocks are small and listed: no syntax colours, no tab "Dependencies", no base type, long Rust namespace names, #336) and criterion 8 (the visual test runs in Hell only, #332). Whether these details block the milestone is the product owner's decision; nothing listed is broken.
