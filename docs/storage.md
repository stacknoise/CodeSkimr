# Storage adapter (`codeskimr_storage`)

SQLite database per workspace, WAL mode, schema migrations in `crates/adapters/storage/migrations/`
(applied at start-up, version in `PRAGMA user_version`). Blueprint 6.2.

## What it does

- Schema version 2 adds `projects.credential`: the name of the credential a Git source logs in with (empty for none). Only the name is stored, never a secret (blueprint 12.2).
- Schema version 3 adds `fingerprints` (`snapshot_id`, `symbol_id`, `position`, `hash`): the syntax fingerprints of the callables (blueprint 10.4). A hash is the 64 bits stored as a signed integer; an index on `(snapshot_id, hash)` serves the similarity query. Databases written before version 3 have no fingerprints until their next full scan.
- Schema version 4 (ADR 0032) stores symbols (`symbol_rows`), metrics (`metric_rows`), references (`symbol_references`) and fingerprints once, without a snapshot id, owned by the file or symbol they belong to. The views `symbols`, `metrics` and `snapshot_references` give every snapshot the rows of its files, with the columns of the former tables. An incremental scan copies only the `files` rows; the prune deletes the shared rows of files that no other snapshot contains. A reference carries the snapshot that wrote it, so older snapshots do not see references that a later scan rebuilt. A new row that points at a file or symbol the snapshot does not hold is refused with STO-901 and rolled back.
- Schema version 10 (ADR 0037) adds `coupling_rows` (`snapshot_id`, `symbol_id`, `kind`, `value`) for `ce`, `ca` and `instability`, which depend on references across files and so belong to one snapshot. The view `metrics` unites them with the shared rows; the prune deletes them with the snapshot.
- Schema version 11 (`0011_pending_references.sql`) adds `pending_references`, the names as written of each file (from, place, kind, name, receiver), shared like the other rows of a file and deleted by the prune with the last snapshot that contains the file, and the column `snapshots.names_stored`, with the indexes `(file_id, from_symbol)` and a partial one for the base lists. `stored_names` reads only the names a scan needs. An incremental scan resolves them again (`docs/incremental-scan.md`, issue #49). A snapshot with `names_stored = 0` is followed by a full scan. `latest_state` reads files and symbols in one transaction; a scan hands the references it no longer produces as `dropped_references`, which the store deletes.
- `SqliteStore` implements the ports `ProjectRepository`, `SnapshotStore`, `CodeIndex`, `UsageIndex` and `SimilarityIndex` (read access for the MCP server: `latest_snapshot`, `search`, `symbol`, `layer_edges`).
- `remove_project` (port `ProjectRemoval`, issue "remove a project") deletes a project in one `BEGIN IMMEDIATE` transaction: every snapshot table by table exactly as the prune does (`delete_snapshot`), then the `projects` row, whose `ON DELETE CASCADE` takes the layers, the level 2 consent, the tool reports and the annotations with baselines and alerts. The test `removing_a_project_leaves_no_rows_in_any_table_and_keeps_the_others` checks every table of the schema. Files on disk and keystore credentials are not part of the database and stay.
- `persist` writes one snapshot and its read models in one `BEGIN IMMEDIATE` transaction, then prunes to the
  retention count. A large full scan (20,000 references or more) prunes first: it drops the reference indexes, deletes the snapshots that fall out of the retention, loads, and builds the indexes again over fewer rows, which is much cheaper than deleting with live indexes. A full scan holds all its references, so its usage counts and the number of references of kind `test` are counted from memory instead of reading the table again (an incremental scan reads the table). Any failure rolls everything back (STO-302 busy/locked, STO-501 disk full, STO-601 other).
- Incremental scans (`ScanMode::Incremental`): files that were not analysed again are copied from the
  previous snapshot with their ids, except the paths in `SnapshotData::removed`; their symbols, metrics and
  references (whose two ends survive) are seen through the shared rows without a copy. Metrics in the new data
  replace stored ones of the same symbol and kind; coupling metrics are not carried but written for every snapshot. The returned stats are the totals of the whole snapshot. `latest_index` returns all symbols
  and references of the newest snapshot, the input of `docs/incremental-scan.md`.
- Statistics (ADR 0091): `symbol_statistics` (one row per type and callable with usage counts, measured values, test flag and the place in the order of path and name), `statistics_facets` and `statistics_complexity` (counts per group), `snapshot_statistics` (which test folders the rows were counted for, sum of the references). Not written by the scan: the program counts them after a scan or a level 2 import in a thread of its own (`CodeStatistics::prepare`) and at the first question if they are missing; a level 2 import deletes the rows of the snapshots it changed. The statistics screen reads its first rows through six partial indexes.
- Read models (rebuilt per snapshot, inside the same transaction): `search_index`, `usage_counts`,
  `type_summary`, `layer_graph`. Queries: `search`, `usage_count`, `type_summary`, `layer_edges`, `symbol_detail`
  (one symbol by id or qualified name with its members and metrics). `usage_counts` and `layer_graph` leave out references of the kind `test` (issue #430); `layer_graph` also leaves out references of confidence `probable`, because a name that matches several symbols is no dependency (issue #464), while `usage_counts` keeps them; the namespace graph of the map (`namespace_graph`) leaves out `probable` and `test` references in the same way; the total `snapshots.refs` still counts every stored reference.
- `UsageIndex` (usages and impact of a symbol, `docs/usages.md`): the references of a snapshot are kept as a `ReverseIndex` in memory for the snapshot that was asked about last; it is built ahead of the first query (at the start of the UI and MCP service) and again after a write of the same project, never lazily after a change (#333); queries of the store wait while it is built. The UI and the MCP service of the running app share one store and so one index (#358), which is why a level 2 import through either is seen by both.
- `SimilarityIndex` (`fingerprints_of`, `similar`): `similar` takes the hashes of the query, counts per stored function how many distinct hashes it shares, and completes the union with the number of distinct hashes of those functions. The percent is the Jaccard value of `Fingerprints::similarity`, rounded down, so it equals what the duplicate check of `docs/conventions.md` computes. The statements take their lists as one JSON text (`json_each`), so the number of hashes is not limited by the number of SQL parameters. A hash that very many functions share makes the count query slow in proportion; capping those is issue #99.
- Outside the ports: `save_project` (registers a project, PRJ-301 for a duplicate source),
  `latest_snapshot`, `next_free_id` (start value for `IdSequence`).

## Known limits

- Search is case-insensitive for ASCII only (SQLite `lower`); the query is lowered the same way.
- The project's layers come from the configuration and are saved with the project at every scan (ADR 0031).
- `layer_graph.violates_layering` is true for an edge from a layer with a `may_use` list to a layer that the list does not name (ADR 0054). Schema version 12 (`0012_layer_directions.sql`) stores the lists in `layer_uses` (`layers.restricted` tells a limit from none); older layers stay unlimited, and the next scan rebuilds the graph.
- `snapshot_warnings` holds the warnings of the scan that wrote a snapshot, one row per error code with a count (schema version 13, issue #433): `RES-301` counts the places that match several symbols and that level 2 has not checked. The count covers the whole snapshot, so an incremental scan writes its own rows and carries nothing over; an older snapshot has no rows. `projects.list` carries them as `warnings` (`code`, `count`) of the project row; the scan screen does not show them as such; it shows the files behind the `PRS-` warnings (see below).
- Schema version 14 (ADR 0055, file `0014_symbol_origin.sql`) adds the column `origin` (`syntax` or `index`) to `symbol_rows` and the view `symbols`. Symbols of origin `index` are created by level 2 and belong to their file; `replace_level2` (`Level2Replacement`: files, symbols, references) replaces them with the references in one transaction, and the prune deletes them with the snapshot.
- Schema version 15 (ADR 0068, file `0015_annotations.sql`) adds `annotation`, `annotation_baseline` and `alert`. They belong to the project (`project_id ... ON DELETE CASCADE`) and to no snapshot, so a new scan and the snapshot retention never touch them and deleting a project deletes them. A symbol is found again by its target key: `target_kind`, `target_name` (qualified name) and `target_params` (the parameter types joined with U+001F, empty for none). A partial unique index allows one `critical` annotation per target; a second one fails with `ANN-301`. `annotation_baseline` holds content hash, signature hash, loc and cc of a critical symbol. `alert` has no foreign key on the snapshot (`snapshot_id`, `commit_hash` only say where the latest sighting was made), and a partial unique index allows one `open` alert per annotation. `AnnotationStore` is implemented by `SqliteStore`: `create_annotation` checks that the fields fit the kind (`ANN-103`) and that kind and qualified name are in the newest snapshot (`ANN-101`; parameter types are not stored in a snapshot, so they are not checked); `update_annotation` re-assigns the target and drops the baseline of the old symbol; `raise_alert` counts the open alert of the annotation once more (and keeps the latest sighting) or opens one; `dismiss_alert` sets the state and writes the given baseline; `purge_dismissed` deletes dismissed alerts older than `annotations.dismissed_retention_days` (the server calls it at its start and every 24 hours; the number of days is read at the start, so a changed setting applies after a restart). Unknown ids fail with `ANN-201` and `ANN-202`. The ids come from `AUTOINCREMENT`, so a deleted id is not used again.
- Schema version 16 (ADR 0068, file `0016_symbol_content_hash.sql`) adds `symbol_rows.content_hash` (the token hash of a type or member, `NULL` for the rest and for snapshots written before), `annotation.without_target`, the columns `alert.seen_content`, `seen_signature`, `seen_loc` and `seen_cc` (what the symbol looked like at the latest `changed` sighting) and, made by the alert step the first time a project has a critical annotation and not by the migration (every scan would pay for them on writing), the indexes `symbols_by_name`, `symbols_by_simple_name` and `pending_references_by_target`. `SqliteStore` implements `SymbolStates` for the alert step: `states` finds symbols by qualified name with their hash, lines and complexity, `child_hashes` collects the hashes below a namespace, `remaining_references` counts the pending names that still point at a removed symbol and `same_simple_name` finds namesakes. `AnnotationStore::refresh_targets` sets or clears `without_target` for the project after a snapshot.
- Schema version 17 (ADR 0072, file `0017_scan_reports.sql`) adds what the newest scan of a project says about itself, in three tables that go with the project (`ON DELETE CASCADE`). `scan_reports` has one row per project: `scanned_at`, `level` (`1`, or `2` if the second pass checked at least one language in this scan) and `origin` (`terminal`, `browser`, `watch`, `mcp`); every scan replaces it. `level2_reports` has one row per project: `run_at` and `origin`; only a scan that ran the second pass writes it, so a level 1 scan of watch mode or MCP leaves it as it is. `level2_languages` has one row per project and language: `outcome` (`checked`, `skipped`, `failed`), `files` and `stale` for `checked`, `reason` for `skipped` (`not_permitted`, `not_confirmed`, `tools_unavailable`, `stale`, `cancelled`, `busy`, `paused`) and `code` for `failed`. Only language ids, counts, keys and error code ids are stored: no path, no tool name or version text, no output of an indexer, no project name (the tool report keeps those). `SqliteStore` implements `ScanReportStore`: `store_report` writes the header of the scan and, only if the scan ran the second pass, replaces the second report and its language rows in one transaction; `report` reads both. A failure to store is the warning `PRJ-502`: the scan and its snapshot stay, and the warning is part of the job result (the snapshot is written before, so it is not stored with it).
- Schema version 18 (ADR 0085, file `0018_snapshot_left_out.sql`) adds `snapshot_left_out` (`snapshot_id`, `path`, `code`, `kept`): the files the scan left out because they alone could not be analysed (`PRS-101`, `PRS-102`, `PRS-501`), at most `scan.max_left_out_listed` per snapshot; the count of all of them is in `snapshot_warnings`. `kept` is true if the file is shown as the previous scan saw it. An incremental scan writes the list of its own run and carries nothing over; the rows go with their snapshot. `projects.list` carries them as `left_out` and `left_out_more`.
- Schema version 19 (ADR 0086, file `0019_ambiguous_places.sql`) adds `snapshots.ambiguous_places`, the number of places of the snapshot that match several symbols (`RES-301`), `NULL` when it is not known: for snapshots written before, for a writer that did not count, and after `replace_level2`, which sets it to `NULL` in every snapshot that holds a replaced file. It also adds the partial index `references_verified` on `symbol_references (file_id) WHERE verified = 1`. An incremental scan reads only the references it needs through `stored_references` (by target, by start, by file or all), `verified_files` and `reference_pairs` (`docs/incremental-scan.md`).
- Schema version 21 (ADR 0093, issue #684, file `0021_snapshot_skipped_files.sql`) adds `snapshot_skipped_files` (`snapshot_id`, `path`, `language`, `content_hash`, `code`): every file the scan left out for good (`PRS-101`), with what it looked like and the code of the failure, without the limit of `snapshot_left_out`. A file whose failure may pass (`PRS-102`, `PRS-501`) has no row. `latest_state` and `latest_head` return the rows of the newest snapshot as `PreviousState::skipped`, and the discover stage takes such a file as unchanged while its hash and language are the same, so that a scan without changes confirms the snapshot. Every scan writes the list of its own run; a scan of some paths passes on the rows of the files it did not look at, and names and counts those files again in `snapshot_left_out` and `snapshot_warnings`, so the snapshot goes on saying that they are left out. `SnapshotStore::confirm` returns the stored list with the warnings, so a scan without changes names the files as the scan that wrote the snapshot did. The rows go with their snapshot.
- Schema version 22 (issue #714, file `0022_project_removing.sql`) adds `projects.removing`. The removal of a project runs in many short writes so that other writes get their turn: it marks the project first, then deletes the shared rows of the files in slices, then the other tables of each snapshot, then the snapshots and at last the project. A marked project is no project for `load_project` (scans, renames and reads answer `PRJ-201`); only the project list and a new removal see it. A removal that stops half way is finished by asking for it again, and the list shows the project as interrupted until then.
- Deleted files are reported by the pipeline (`SnapshotData::removed`); the store trusts that list.
- Schema version 7 adds `tool_reports` (one row per project: `project_id`, `checked_at`) and `tool_findings` (language, tool, role, state, found and required version; `state` is text and holds `ready`, `missing`, `not_runnable`, `too_old`, `too_new` or `version_unknown`, so `too_new` needed no migration). `ToolReportStore` replaces the whole report of a project in one transaction and reads it back; a project that was never checked has none. `ProjectCatalog::languages` lists the languages of the newest snapshot with files and lines of code. Databases of version 6 get empty tables.
