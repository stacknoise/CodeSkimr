# Level 2: running the indexers (ADR 0033, package 4)

`crates/adapters/indexer` (`codeskimr_indexer`) starts the indexer of a language as a child process and returns its SCIP index. The port is `IndexRunner` (`crates/application/src/ports/indexer.rs`), the rules of consent are in `crates/application/src/level2/`. The import of the index is `docs/level2-import.md`. Nothing calls the runner from the scan yet; that is the second package.

An indexer runs the build tools of the project, which is project code. So the runner is security sensitive, and everything below is tested (`crates/adapters/indexer/tests`, with a stand-in program instead of a real indexer, `crates/application/tests/level2.rs`).

## Who may start it (decisions 9 and 10)

- Level 2 runs only if the user enabled it for the project **in the user configuration (`level2.enabled`) or in the user's own project record** and **confirmed it once** (the record, table `level2_consent` of the database). `authorize_run` checks both.
- The `level2` table in the project's `.codeskimr.toml` is dropped before the files are merged (`Config::resolve`), so a scanned repository can neither enable level 2 nor raise a limit. Test: `the_project_file_cannot_switch_level_2_on_or_raise_its_limits`.
- Two permissions, `confirm_indexer` and `run_indexer`. Only the local owner holds them. A principal without them gets `SEC-403`. MCP, REST tokens, watch mode and CI have no way to confirm: only `level2::confirm` writes the record, and the screens and commands of the local owner are its only callers. Without the record they get `SEC-301`.
- **Bound to the source.** The confirmation stores the kind, location and branch the project had; the store reports `confirmed` only while the project still has them. A project that is pointed at another folder or repository (or an id that is assigned anew) is unconfirmed again. A Git source can change its content at the same place (a pull); that is covered by "confirmed once" and belongs in the confirmation text.
- **Proof, not convention.** `authorize_run` returns a `RunPermit` that only it can create, and `IndexJob` needs one. The runner calls `permit.recheck()`, which reads the consent again, right before it starts the process. A withdrawal in between gives `SEC-301`.

## What the runner does (decision 11)

1. **Program.** Looked up in the `PATH` of the application as read at start. Relative entries and entries inside the project are dropped from `PATH`, also for the indexer, so a repository cannot plant `dotnet` or `node` in its own folder. Never `npx`, never a download. On Windows `.exe`, `.cmd` and `.bat` are tried.
2. **Tools checked first.** The indexer and every tool of the toolchain are asked for their version in a neutral folder (not in the project: the `rustup` proxy and `dotnet` read files of the working folder). Missing or older than `min_version` gives `RES-201` with the tool names in the cause. `IndexRunner::check` does the same without running an indexer, for the tool check on load (decision 8, which another package builds).
3. **Environment.** Built from an allow list (`consts.rs` of the crate plus `env_allow` of the pack), never inherited. A name that contains `TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIAL`, `API_KEY`, `PRIVATE_KEY` or `AUTH`, or starts with `CODESKIMR`, never passes, even if a pack lists it. `TMPDIR`, `TEMP` and `TMP` point into the output folder. **Empty home (issue #222), for tools that respect `HOME`:** `HOME` and `USERPROFILE` (and `APPDATA`, `LOCALAPPDATA`) point to an empty folder inside the output folder, never to the home of the user, so a tool that looks for `~/.ssh`, `~/.aws`, `~/.npmrc` or `~/.git-credentials` finds nothing. What a tool needs from the real home is named by the pack in `home_dirs` (variable and folder below the home, such as `CARGO_HOME = ".cargo"`); the runner sets the variable to that folder only if it exists and the application did not pass the variable itself. These folders are named on purpose and are readable, and some hold credentials of their own: `CARGO_HOME` (`.cargo/credentials.toml`, the registry token; no narrower folder is possible, because `cargo` finds registry cache and binaries below it), `GRADLE_USER_HOME` (`gradle.properties`), `NPM_CONFIG_CACHE` (`.npm` is the cache and logs, the token of npm is in `~/.npmrc`, which stays unreachable) and the Maven repository (`~/.m2/settings.xml`, not named by any pack: Maven downloads into the empty home). That is why the confirmation text stays honest about file access. Java (`user.home` comes from the user database) and .NET on Windows (known folders) ignore `HOME` and `USERPROFILE`, so for the Java, Kotlin and C# packs the empty home does not reliably protect `~/.ssh` and the like. A variable of `home_dirs` whose name says it holds a secret (the parts of the rule above) is never set.
4. **Output.** A folder inside the data directory (`level2-…`), removed when the returned `IndexArtifact` is dropped, also when the run fails. The index goes to `{output}`.
5. **Process group.** Own process group on Unix, a job object on Windows (crate `process-wrap`, no `unsafe` in our code). On timeout, memory or output limit, cancel and at the end of every run the whole group is killed, so build servers and daemons that the build started do not stay. **Hard stop of CodeSkimr (issue #223):** `kill -9` or a crash runs none of that, and `process-wrap` 10 gives the job object on Windows no `KILL_ON_JOB_CLOSE` (and a parent-death signal on Unix needs `unsafe`). So every output folder holds two notes: `owner` (the application's process id and start time) and `indexer` (the same for the process it started). Before the first run after a start, the runner reads the notes of all `level2-*` folders; where the owner is no longer running, it kills the noted process and everything still below it and removes the folder. A process is identified by id and start time (two seconds of difference are tolerated, because the start time derives from the boot time), the start time is read again right before the kill, and this process and its parent are never killed, so a recycled id is practically never touched. The notes lie in the run folder, which the indexer can write: it could name another process of the user in them, and the next start would end it. That is within what an indexer without a sandbox can do anyway (see below). A `data_dir` shared over a network between computers is not supported: the owners of the other computers would count as ended. A folder without a note is left alone for 60 seconds, and a run whose owner note cannot be written does not start (otherwise another instance would take its folder for abandoned after that time and end it). The nested processes of a left-behind indexer are collected by parent id and start time (a child never started before its parent), because on Windows the parent id stays after the parent has ended. Limit: processes that already lost their parent (for example daemons of a build) are found only while the noted process is alive; a probe of a tool version (20 s) is not noted.
6. **Limits.** `level2.timeout_seconds` (`RES-502`), `level2.max_memory_mb` for the resident memory of the whole process tree, polled every 250 ms (`RES-504`; crate `sysinfo`), `level2.max_output_bytes` for console plus files of the output folder (`RES-503`); a folder nested deeper than the measure goes counts as over the limit. A cancelled run is `PRJ-303`.
7. **Redaction.** The console output goes through the redaction function that the composition root passes in (`redact` of the app) first and is cut to its last 2 KiB afterwards, so a secret at the cut is masked whole; the same holds for the version output in `RES-201` (200 characters). It is logged or put in an error (`RES-601`) only like that. The index file must be a regular file, not a link (the scan opens it with `O_NOFOLLOW` on Unix and `FILE_FLAG_OPEN_REPARSE_POINT` on Windows and checks the type on the opened handle, so a link cannot be put in place between check and open, issue #229). The runner logs nothing else of the output.

## Not done here

- The indexer builds in the project folder (`obj`, `bin`, `target`, `node_modules`); that is not counted against the output limit. Folders inside the project are removed from `PATH`, so a virtual environment inside the project (`.venv`) is not found for scip-python; the user activates it outside or installs the tools globally.
- The permit carries the folder of its project (`RunPermit::project_root`), so a permit cannot be used with another project's folder. The caller must take the id and the folder from the same project record.
- The network is not blocked (restoring dependencies needs it); that stays the main residual risk of decision 11 and the reason for the consent.
- **Sandbox, evaluated (issue #222).** Not built, for these reasons. Linux Landlock restricts files well but needs a new dependency (`landlock`) and a kernel from 5.13, and it can only restrict the network from ABI 4 (kernel 6.7), and then only by port, while a build needs the network for its restore and must read the system folders and the toolchain. `bwrap` is a program the user would have to install, and it needs user namespaces, which many distributions and containers switch off. A Windows AppContainer needs direct calls to the Win32 API, which means `unsafe`, allowed only in `codeskimr_secrets::memory`. A sandbox that is switched off on half of the systems would give a false feeling of safety, so the confirmation text states that the indexers are not sandboxed. What is done instead: the empty home above, the environment allow list, and the honest text. A real sandbox needs an ADR (new dependency and technology, blueprint rule 9) and is tracked in its own issue.
- The memory limit is polled: a process that allocates very fast can exceed it for up to a quarter of a second.
- A test with the real `redact` of the app (Bearer line, URL with credentials, secret across the cut) comes with the wiring, because the indexer crate cannot depend on the app.
- Files and network: the indexer can still read what the user can read, by absolute path, and use the network; the empty home only removes the default places of credentials.
- Confirming needs a screen or command of the local owner (the second package, with the wiring into the scan).

## Who starts indexers

Only the scan of the command line (`codeskimr scan`, first scan of watch mode) runs the second pass. `ProjectScanner::rescan`, which MCP and the UI use, builds its job without level 2 (a `Job` wants it only through `with_level2()`, which only the scan of the command line calls), so an AI agent or a browser client can never start the build tools of a project, even after the owner confirmed level 2. Later scans of watch mode are level 1 too. `mcp` and `serve` also run as `principal::remote_client()`, which holds neither `ConfirmIndexer` nor `RunIndexer`. A test in `crates/application/tests/scan.rs` pins all three. The confirmation is bound to source, location and branch, not to the commit (issue #230).
